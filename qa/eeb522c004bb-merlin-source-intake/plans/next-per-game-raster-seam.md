# Per-created-game raster artwork: next bounded seam

Human correction: the game decides its artwork, it must be created for that game, and the repeated cover pictures shown in the card-back checkpoint look bad. Do not call those fixtures acceptable bespoke art.

Observed source: apps/worker/src/cover-generation.ts only asks a text model for a palette/layout/motif/seed and explicitly forbids images; every output is renderCoverSvg(), with procedural SVG fallback. The new card-back file handoff supports actual raster bytes but does not create them. Known-title defaults and cover reuse do not satisfy game-specific creative generation. Custom nonstandard card fronts still have a separate richer-art runtime gap.

Primary provider reference: official openai/openai-node repository, ordinary HTTPS Git clone, exact commit4bfed1f69fc0e86e7da0657df8d54b6e99118c02, src/resources/images.ts. The SDK documents POST images/generations; explicit model selection; portrait1024x1536; WebP output_format plus output_compression; b64_json results for GPT image models. It also documents current model retirement, reinforcing that the app must require an account-configured image model rather than hard-code one. This read is provider documentation, not evidence of account access or live generation. No credentials or model invocation were provisioned.

Alternatives: randomizing or reusing sample cover art still fails the human's request. Requiring manual upload can support editing but cannot be the one-prompt completion path. The useful next slice is game-authored art direction plus actual raster image jobs through the normal creation/edit/play path, with explicit asset-specific completion/retry. Cover art and a concealed-card back need separate compositions; a busy cover with miniature cards and tiny text should not automatically become the back.

Acceptance for one coherent slice:
1. Generated game output specifies a concrete coherent art direction and distinct image briefs for its cover and main card-deck back. Additional deck-specific backs remain an explicit incomplete requirement for multi-deck games such as Merlin. Briefs use actual game theme/mechanics/source material; no fixed game/sample image mapping.
2. Provider settings reuse existing authorized access and require an explicitly selected image model. Missing image access is a visible pending state, preserving the validated rules/art plan and an editable backup; it cannot be reported as complete artwork or trigger repeated rule generation.
3. Image requests are bounded, authenticated and metered; process only base64 raster results through actual header/hash/pixel decoding and the existing size/alpha/crop protections. Preserve exact originals and processed hashes plus prompt/model provenance. No silent SVG/stock fallback.
4. Pin generated backs in the normal versioned presentation bundle and cover metadata outside canonical state. Two independently created game identities own distinct asset/provenance records and caches. Retry must reuse completed assets and preserve old published versions.
5. Creation automatically completes available jobs and opens the actual game with them; the ordinary editor can revise art direction/regenerate without throwing away rules. Storage/provider/decode failure and retry must remain usable on desktop/390px/short heights, with clear pending/ready labels and reachable downloads/credits.
6. Exercise the complete source→game-art-brief→raster-job→decode→private play→editable backup→publication/reload path using identifiable local raster/provider-port fixtures when no image provider exists. Label those transport/rendering fixtures explicitly. Genuine provider output and perceptual art quality remain pending until actual access/output exists.
7. Review the actual rendered image as a back: coherent motif, readable silhouettes, strong small-scale contrast, adequate safe edges, no tiny copy/miniature box art, and no hidden identity hints. A deliberate symmetric back is different from its cover. Human approval of style and a fun game cannot be inferred from automated test counts.

Merlin remains the real acceptance target, with v0.1.27b and seven linked Google Sheets as sources. Full-source intake is the current prerequisite being closed; no simplified fixture or hand-authored substitute is a full Merlin generation pass. Broad custom-card art, image atlases, multi-deck bindings, 3D assets, music and further audio are subsequent seams, not completed by this bounded cover/back path.
