SPEC 00 - Executive Brief
Status: Normative
Purpose: Define the product, governing architectural thesis, non-negotiable principles and phased delivery model.
00.1 Product summary
Build a browser-native multiplayer tabletop platform with an integrated creator environment. Users create tabletop games 
visually and with Lua, playtest locally or online, publish immutable releases, browse community games, host live tables, invite 
friends, and play directly in the browser.
CREATE -> PLAYTEST -> PUBLISH -> BROWSE -> HOST -> INVITE -> PLAY
The intended product category is a web-native tabletop game runtime and UGC platform, not a single board game and not a 
general-purpose realtime video-game engine.
00.2 Core user promise
PRINCIPLE-001 - Browser native - MUST
A player receiving a valid invite link can join and play without installing native software.
PRINCIPLE-002 - Low-friction joining - MUST
An unauthenticated guest can join an invite-only table without creating an account. Target flow: invite link -> display name -> 
load -> table.
PRINCIPLE-003 - Immediate interaction - MUST
Normal local tabletop manipulation visually responds without waiting for network acknowledgement.
PRINCIPLE-004 - Creator accessibility - MUST
A creator can assemble a basic tabletop game without Lua; Lua adds behavior and rules.

00.5 Locked architectural requirements
ARCH-001 - Deterministic kernel - MUST
Canonical gameplay executes through a deterministic Game Kernel.
ARCH-002 - Rendering separation - MUST
Babylon.js is presentation/rendering infrastructure, not canonical authority.
ARCH-003 - Host independence - MUST
Original room Host is not simulation authority; host disconnection does not end the table.
ARCH-004 - Ordered canonical actions - MUST
Canonical gameplay is reconstructable as starting snapshot + ordered actions.
ARCH-005 - Rollback/replay - MUST
Clients support rewind/replay enough to reconcile prediction and late canonical ordering.
ARCH-006 - Room coordinator - MUST
Each active table has one logical Durable Object room coordinator under the baseline architecture.
ARCH-007 - Backend does not simulate game rules - MUST
The Room DO sequences and coordinates; it does not run ordinary game-rule simulation or Babylon physics.
ARCH-008 - Canonical WebSocket path - MUST
Canonical gameplay remains operational through WebSocket when WebRTC is unavailable.
ARCH-009 - WebRTC optional - MUST
WebRTC is transient/presentation optimization only.
ARCH-010 - Deterministic randomness - MUST
Canonical randomness uses a versioned deterministic PRNG included in canonical state.
ARCH-011 - Immutable releases - MUST
Published playable releases are immutable.
ARCH-012 - Compatibility - MUST
Published releases pin compatibility information required to retain gameplay semantics.
ARCH-013 - Lua isolation - MUST
Creator Lua has no unrestricted JS/DOM/network/storage/filesystem/OS access.
ARCH-014 - Persistent Lua state - MUST
Persistent gameplay state controlled by Lua is Kernel-managed serializable state.
ARCH-015 - Playtest isolation - MUST
Playtest mutations never modify authored project state.
ARCH-016 - Presentation physics - MUST
Cross-browser deterministic rigid-body physics is out of scope; physics may be local presentation.
00.6 Security model
SEC-001 - UI-private information - MUST
The official client respects private hands, face-down cards, hidden containers and logical visibility.
SEC-002 - No hostile-client secrecy guarantee - MUST
MVP does not claim secrecy against a modified participant client. Do not market it as cryptographically secure competitive 
hidden-information infrastructure.
SEC-003 - Backend authorization remains trusted - MUST
Friendly multiplayer semantics do not weaken authorization for projects, publishing, room administration, saves or moderation.

SPEC 02 - UX & Interaction Specification
Status: Normative
Purpose: Define player and creator behavior precisely enough that implementation and QA do not invent workflows.
02.1 UX principles
UX-001 - Table first - MUST
The 3D tabletop is the visual priority during play.
UX-002 - Progressive complexity - MUST
Player-facing interaction is substantially simpler than creator-facing interaction.
UX-003 - Direct manipulation - SHOULD
Prefer direct manipulation where the object metaphor supports it.
UX-004 - Recoverable actions - SHOULD
Ordinary reversible editor actions rely on Undo rather than unnecessary confirmations.
UX-005 - Explicit destructive actions - MUST
End Table, Project deletion, kick and public-content removal require confirmation.
UX-006 - Technical failures hidden by default - MUST
Players see human-readable errors; low-level sequence/hash/socket/Lua details stay in diagnostics.
02.2 Home, join and loading
HOME
[ JOIN TABLE ]  [ HOST GAME ]
[ BROWSE GAMES ]
[ CREATE A GAME ]
Join accepts room code or supported invite URL, normalizes formatting, resolves the room, requests guest display name if 
required, and proceeds directly to the Table. Loading visibly advances through connecting, loading release/assets and starting 
simulation. Missing, ended, full and failed rooms have distinct recovery actions.

02.5 Cards, decks, hands and dice
Deck supports Draw to Hand, Draw to World by dragging from top, Shuffle, Deal and Inspect. The client never chooses which

02.7 Reconnect and rollback UX

SPEC 03 - Deterministic Game Kernel
Status: Normative architecture
Purpose: Define canonical gameplay semantics independent of UI, rendering and Cloudflare implementation.
03.1 Definition
For valid initial snapshot S, ordered action stream A and kernel version K:
run(K, S, A) = identical canonical state
KRN-DEP-001 - Dependency exclusions - MUST
Kernel has no React, Babylon.js, DOM, WebRTC, Cloudflare APIs, browser wall clock, localStorage, IndexedDB, Math.random 
or presentation physics dependencies.
KRN-DEP-002 - Headless execution - MUST
Kernel runs in a headless Bun/Node-compatible test environment without DOM shims.
03.2 Canonical state
CanonicalGameState {
  schemaVersion
  sequence
  releaseId
  kernelVersion
  settings
  rng
  players
  seats
  entities
  scriptState
  prompts
}
Canonical values are finite JSON-like primitives, arrays and string-keyed objects. Functions, Promises, DOM/Babylon objects, 
VM pointers, cyclic graphs and unsupported nonfinite numbers cannot enter canonical state.
03.3 Ordered actions and rejection
Every service-accepted OrderedAction consumes one monotonically increasing Sequence. Game-semantic rejection still 
advances processed Sequence but does not mutate gameplay fields. All top-level action processing is transactional: if a script 
or generated subcommand fails, all uncommitted gameplay mutation is discarded.
03.4 Mutation boundary and registry
Canonical state changes only via a registered canonical action or deterministic subcommand generated during the current 
transaction. Each action has type/version, allowed sources, payload schema, validation/application logic and event metadata. 
Player, script and system sources are validated independently of UI visibility.
03.5 Identity, transforms and location
Entity IDs are immutable and never reused after destruction. Spawned IDs derive deterministically from canonical action identity 
plus spawn index. Canonical transforms reject NaN/Infinity/invalid quaternion/out-of-bounds values and are 
normalized/quantized before hashing. High-frequency drag transforms are transient; only Grab and final Drop are canonical.
03.6 Tabletop invariants
• Container membership has one canonical source of truth.
• Deck is Container semantics + Deck capability; last item is top in v1.
• Shuffle uses deterministic RNG and never accepts a client-provided resulting order.
• Draw/deal derive card identity from canonical Deck contents; insufficient requested cards reject transaction.
• Hand is Container + owner/visibility semantics; visual sort is local unless canonicalOrder enabled.
• Die Roll consumes deterministic RNG; animation never chooses canonical result.
• Counter set/add clamps to optional bounds.
• Zone membership is recomputed on semantic placement transitions, not frame physics.
• Snap resolution filters valid candidates, picks nearest, then stable SnapPoint ID on exact tie.

03.7 RNG, serialization and hash
RNG algorithm is explicit, versioned and snapshot-visible. Gameplay RNG is separated from presentation randomness. 
Canonical serialization defines UTF-8 representation, object key ordering, number normalization, array ordering, null semantics 
and unsupported-value rejection. SHA-256 is the baseline StateHash. Hash is over canonical serialization, not compressed 
bytes.
03.8 Snapshot, replay, rollback and prediction
GameSnapshot { formatVersion, kernelVersion, releaseId, sequence, state, stateHash }
Snapshot load must reproduce the stored hash. Rollback implementation may use local snapshots, patches or persistent 
structures, but must converge to the same final hash as uninterrupted canonical execution. Prediction is initially recommended 
for grab/drop/flip/button/simple counter/prompt responses, and conservative for random/large scripted actions.
03.9 Lua and timers
Canonical Lua executes inside action transactions and can only queue deterministic Kernel mutations. Persistent Lua state is 
Kernel-owned. Script errors abort the top-level transaction. Execution budgets limit instructions/operations, memory, generated 
commands, recursion and persistent state size. Timers are scheduled by room service and become canonical system.timer_fire 
actions.
03.10 Kernel acceptance invariants
same snapshot + actions = same hash
snapshot/load preserves hash
rollback/replay = uninterrupted execution
rejected action has no partial gameplay mutation
RNG replay identical
destroyed IDs never reused
exclusive Entity in at most one container
held Entity has at most one holder
invalid transform cannot enter state
script failure atomic
query and generated-command order deterministic

SPEC 04 - Lua API v1
Status: Normative creator API
Purpose: Define the stable scripting surface and sandbox expectations for deterministic tabletop rules.
04.1 Philosophy and environment
Lua expresses tabletop rules, not browser/renderer implementation. The v1 environment exposes state, refs, settings, game, 
scene, players, random, timer, ui and data. Entity scripts additionally receive self and props. Unsafe 
browser/network/storage/filesystem/OS and arbitrary JavaScript access are unavailable. require() resolves only packaged 
project/platform modules.
refs.main_deck:shuffle()
refs.score:add(1)
ctx.player.hand:add(card)
self:flip()
04.2 Persistent state
If a value affects future gameplay, it belongs in state. Persistent values are canonical-compatible nil/boolean/finite 
number/string/tables. Functions, userdata, proxies, cycles and nonfinite numbers cannot persist. Fresh VM + Release code + 
canonical state must reconstruct gameplay behavior.
04.3 refs, settings, props and self
• refs resolves stable editor-defined Entity references by identity; rename does not break it.
• settings is read-only canonical room-start configuration.
• props contains editor-authored per-binding configuration.
• self is the Entity proxy for an entity-bound script. Destroyed proxies become invalid safely.
04.4 Core namespaces
scene:get(id)
scene:find(name)
scene:query({tags={"enemy","unit"}})
scene:spawn(prefabId, options)

random:int(min,max)
random:float()
random:choice(list)
random:shuffle(list)
All collection/query ordering that can affect canonical scripts is explicitly deterministic. Recommended scene:query ordering is 
ascending stable EntityId; player ordering uses stable seat order then PlayerId for unseated participants.

04.6 Timers and prompts

timer:cancel(timer_id)
ui:prompt(player, { id="action", title="Choose", choices={...} })

Timer callbacks are named, not anonymous closures, so they survive reconstruction. Prompt state is canonical and response

04.7 Callbacks and guards
Game: on_start, on_player_join, on_player_disconnect, on_player_removed, on_prompt
Entity: on_click, on_grab, on_drop, on_flip, on_spawn, on_destroy, on_roll, on_press, on_enter, on_leave, 
on_container_add, on_container_remove
Guards: can_click, can_grab, can_drop, can_flip, can_press
Guards are read-only. They may allow/deny and optionally return a user-facing reason, but cannot queue canonical mutations. 
Event subscribers execute in deterministic stable ScriptBindingId order. Normal event callbacks may queue subcommands 
FIFO inside the parent transaction.
04.8 Failure and budgets
Canonical script errors record script/binding/function/line/message/Sequence and abort the top-level transaction. Infinite loops, 
recursion, command explosion and memory growth are bounded. Wall-clock timeout alone is not sufficient as the sole 
deterministic guardrail. Phase A must prove a viable instruction/operation budget strategy.
04.9 Example
function on_start(ctx)
    state.turn = 1
    refs.main_deck:shuffle()
    for _, player in ipairs(players:list()) do
        if player.hand then refs.main_deck:deal(player, 5) end
    end
end
function can_grab(ctx)
    return ctx.player.seat.id == props.seat_id, "Only this seat may move this piece."
end

SPEC 05 - Multiplayer Protocol & Room Service
Status: Normative realtime protocol
Purpose: Define room lifecycle, sequencing, reconnect, prediction, checkpoints, timers, WebRTC and failure handling.
05.1 Core principle and lifecycle
Client requests -> Room Durable Object -> Canonical order -> Every client runs identical Game Kernel
CREATING -> ACTIVE -> EMPTY -> ENDED
Identifiers are distinct: RoomId, JoinCode, PlayerId, ConnectionId, RoomSessionToken, RequestId, ActionId, Sequence, 
CheckpointId and TimerId. A reconnect creates a new Connection for the same Player.
05.2 Create, join and session
Room creation validates Release readiness/permission/settings, allocates RoomId and JoinCode, chooses canonical seed, 
initializes room state and joins Host. Join validates room/capacity/spectator policy and returns RoomId, PlayerId, session token, 
ReleaseId and WebSocket endpoint. Session tokens are unguessable, room/player scoped, revocable and never public.
05.3 Handshake and recovery
hello { protocolVersion, sessionToken, lastSequence }
response:
bootstrap | resume | resync_required | protocol_error | room_ended
Recent reconnect receives missing actions. Stale or divergent client loads a confirmed checkpoint, verifies hash, replays later 
actions, then resumes. Sequence gaps are detected; clients never silently skip missing canonical actions.
05.4 Canonical action request and sequencing
action_request { requestId, predictedAtSequence, action:{type,payload} }
ordered_action { sequence, actionId, requestId?, actor, action }
Room service validates protocol/session/rate/size but does not run game-specific Lua or semantic validation. Actor identity 
comes from authenticated room session, not client payload. Each unique service-valid request receives exactly one Sequence. 
Duplicate RequestId returns/rebroadcasts the original mapping and never creates a second action.
05.5 Prediction and reconciliation
Client maintains confirmed state plus pending local predictions. Matching requestId confirms placement in the canonical stream. 
If intervening canonical actions invalidate a prediction, client rolls back to a confirmed point, applies canonical actions, then 
replays still-valid predictions. Final canonical hash must match clean canonical execution.
05.6 Checkpoints and hash consensus
Room retains a bounded recent action window. Client-generated checkpoints include sequence/hash/snapshot/release/kernel 
version. With multiple healthy clients, room seeks at least one additional matching hash before confirming a checkpoint where 
practical. v1 is friendly-mode, not Byzantine consensus. Hash mismatch triggers automatic resync and telemetry.
05.7 Disconnect, seats and host
Transport loss first marks a Player reconnecting; no game-level disconnect action is emitted until grace expiry or explicit leave. 
Canonical player departure releases held objects. Host is room-service metadata, normally migrating to the oldest connected 
non-spectator. Host identity is not exposed as v1 gameplay state. Kick revokes session and emits canonical player.removed.
05.8 Timers and empty rooms
Room service schedules canonical timers from Lua registrations. Due timers become system.timer_fire exactly once. One-shot 
timers survive service restart without duplicate firing. Empty rooms pause ordinary game timers by default; room expiration is a 
configurable operational policy, baseline around 30 minutes.
05.9 WebRTC transient path
WebRTC carries only transient drag previews, remote cursors and laser pointers. Full mesh is the 1-8 player baseline subject to 
Phase A. Transient channel is unordered/unreliable/latest-state-wins. If unavailable, transient data may use a rate-limited 
WebSocket fallback. Disabling WebRTC entirely must not prevent correct game completion.

Status: Normative editor specification

06.1 State boundaries
Project State = persistent authored content
Editor State = selection/tabs/layout/camera/gizmo preview
Runtime State = active Game Kernel playtest
Persistence State = revision/saving/conflict/offline
All authored mutations pass through editor-core. React requests commands; Babylon reports interactions and projects state 
visually. Neither directly owns Project persistence.
06.2 Commands, undo and autosave
Every authored structural/property change is an EditorCommand or transactional group. One semantic Add Card or transform 
drag produces one Undo step. Runtime Playtest actions never enter editor Undo history. Autosave uses monotonically 
increasing Project revisions and expectedRevision conflict protection.
06.3 Single-writer and recovery
MVP allows one active write lease per Project. A second editor can open read-only or take over, invalidating the prior writer. 
Lease loss is visible and unsaved local changes are recoverable rather than silently discarded. Browser local recovery buffer 
protects against crash/network loss; full offline-first editing is out of scope.
06.4 Hierarchy and Inspector
Hierarchy operates on stable Entity IDs and supports select, rename, reparent, duplicate, delete, search and context actions. 
Display name is never identity. Reparent preserves world transform by default. Ordinary component inspectors are schema-
driven; rich components such as Deck, Seat, Script and Game Settings may use custom inspectors.
06.5 Prefabs
Prefab is a reusable Entity hierarchy with stable local IDs. Instances retain source linkage plus explicit overrides. Updating a 
Prefab updates inherited values but does not erase overrides. Orphaned overrides are surfaced. Unpack Prefab converts to 
ordinary independent Entities. v1 prohibits nested live Prefab instances to avoid override/cycle complexity.
06.6 Assets
Asset states: Uploading, Processing, Ready, Failed, Archived. Supported MVP imports: GLB and PNG/JPEG/WebP. Uploads 
are untrusted and server-side processed/validated. Release references immutable processed runtime content, not raw uploads. 
Models cannot cause arbitrary runtime fetches to creator-controlled origins. Asset deletion never deletes bytes still referenced 
by Releases/Saves.
06.7 Scripts and diagnostics
Lua scripts have stable ScriptId independent of filename. Entity script bindings have stable BindingId and props. CodeMirror 
provides Lua highlighting, line numbers, search, folding, autocomplete, API hover and diagnostics. Problems are structured 
Error/Warning/Info entries; Runtime diagnostics show Sequence, StateHash, recent actions, script errors, prompts, timers and 
RNG summary.
06.8 Build, playtest and online test
Validate -> Resolve Scenes -> Resolve Prefabs -> Resolve Refs -> Validate Components/Settings/Seats -> 
Validate Lua -> Validate Assets -> Normalize Runtime -> Generate Initial Template -> Manifest -> Hash
Local Playtest freezes a Project revision/snapshot and uses the same runtime concepts as Online Test and Published play. 
Editing is read-only while Playtest runs in v1. Stopping disposes runtime and restores unchanged authored state. Online Test 
builds an immutable temporary unlisted Release and normal room; editing requires stopping/rebuilding rather than hot-mutating 
the running deterministic session.

10.3 Declarative behavior layer

A versioned deterministic Lua standard library sits above the Kernel API. Initial recommended modules are turns, rounds, 
scores and teams.

Creator-facing errors answer: what happened, where, why and how to fix it. Raw Lua/engine traces are secondary advanced
